# YuPay — Module Map

Each module owns its tables and exposes a narrow Python interface via `apps/api/src/yupay/modules/<name>/api.py`. Other modules call `api.py` or react to outbox events. This is the single rule that keeps future microservice extraction a refactor rather than a rewrite.

**No cross-module SQL _writes_, and no cross-module joins on the request path's write side.** A module never `UPDATE`s or `INSERT`s into another's tables — that is the invariant, and it has no exceptions. Read-only joins into another module's tables are permitted **for a read model**, where the alternative is an N+1 across a module boundary that no amount of batching in `api.py` can fix: `merchants/price_list.py` (the B2B price list joins `brands`/`products`/`skus`), `merchants/admin.py` (merchant balances joined from `wallet_*`), `integrations/merchant_feed.py` and `admin/service.py` all do this deliberately. The extraction cost is real and accepted: each such join becomes an API call the day a module moves out, which is why they are listed here rather than left to be discovered.

Retail `active` is deliberately not read, and a costless SKU is absent rather than free. Money leaves this surface as a two-decimal JSON string (`machine_schemas.UsdBalance` / `UsdPrice` — a balance rounds down, a price up, matching `pricing.merchant_price`). A SKU whose markup fails `pricing.violates_margin_floor` is withheld too, so the price list cannot advertise what the order path would refuse. `/merchant/v1` is **exempt** from the coarse slowapi limiter (`bootstrap._exempt_self_authenticating_routes`): its own two-axis guard answers RFC 7807, and at equal ceilings the middleware would otherwise win the tie on a polling caller and return a non-conforming body. Task 4 adds the money path: `POST /merchant/v1/orders` (`orders.py`) — one SKU, priced by `pricing`, reconciled against the caller's `expected_price` by `pricing.price_to_charge` (spec §8.4 as amended by the owner 2026-09-07, ADR-0069: the ±2% band is an accept/reject tolerance, never a bid — drift ≤ ±2% executes at **our** current price, beyond it is `422 price_changed`), floored by the same `violates_margin_floor` the catalog applies, charged to the deposit by `deposit.charge_deposit` (`C merchant_deposit / D house_payments_received`, `SELECT … FOR UPDATE` on the deposit row as the overdraw guard, ledger key `merchant-order:{order_id}`), then born **paid** and handed to fulfilment — all in one transaction. Fulfilment is **always enqueued**, never inline: the call site forces `fulfilment_async` on (`orders.py::_enqueue_only`) so a supplier purchase can never sit inside the transaction that debits the deposit, since a rollback after the supplier is paid would leave no order, no debit and no record while the merchant retries the same `merchant_order_id` and buys twice. It reuses `orders.create_order` through a merchant-only `unit_price_usd_override` seam rather than forking it, is idempotent on the reseller's `merchant_order_id` and not on an `Idempotency-Key` header (spec §9.3, AGENTS §9), refuses an `affiliate_code` on the merchant arm, and never mails anyone (`notifications._delivery_recipient` returns `None` for a merchant order by an explicit guard). See `sequence-diagrams/merchant-order-create.mmd`. Task 5 adds the two reads a reseller's back office lives on, completing the five endpoints v1 ships — spec §9.1 sketches a sixth, `POST /merchant/v1/validate/…`, deliberately left out because a validator is honest only where a real player-check provider covers the SKU. `GET /merchant/v1/orders/{merchant_order_id}` (`order_status.py`, `sequence-diagrams/merchant-order-read.mmd`) returns status, timeline, failure reason, refund mark and **the delivered voucher code** — deliberately, because M3's `order.status_changed` webhook will not carry it. It is declared with Starlette's `:path` convertor because `merchant_order_id` may contain `/` (the auth README's worked example is `my%2Forder`): the segment is percent-decoded before it is matched while the signature still covers the raw request line. Scope is the authenticated merchant via `orders.find_merchant_order`, and another merchant's order answers with the byte-identical `404 order_not_found` a nonexistent id gets, so there is no oracle for a competitor's order numbering. The artifact is filtered through `fulfillment.buyer_safe_artifact`, the storefront's own allow-list, moved from `fulfillment/routes.py` to `fulfillment/service.py` so both surfaces share one list; `failure_reason` is a closed vocabulary read off the order **item**'s state, which inherits fulfilment's rule that a low-supplier-balance failure stays hidden from the buyer. `GET /merchant/v1/transactions` (`transactions.py`) pages the merchant's own deposit ledger through M1's grouped query (`deposit.list_deposit_transactions`, shared with the admin panel rather than re-summed) with a **keyset** cursor on `(created_at, id)` — not OFFSET, because the ledger is written while it is read and an inserted row would make an offset page repeat a charge. The module was split by responsibility in the same task: `service.py` (the account), `credentials.py` (its API keys), `deposit.py` (its money and the ledger listing, moved out of `admin.py`), `quote.py` (what may be ordered and at what price) and `orders.py` (placement). Cycles are prohibited. When a "downstream" module needs to influence an "upstream" one, it does
so by emitting an event consumed by the upstream module's handler — not by importing it.

`scheduler` (dotted edge above) is not a `yupay.modules.*` package — it's the
separate `apps/scheduler` process. The dotted line marks it as an
out-of-process dependency rather than a Python import: the `broadcast_dispatch`
job reads/writes `broadcasts`' own tables directly and calls the
`notifications` Telegram channel itself, so `broadcasts`' delivery path
depends on that process running, without `broadcasts.api` ever importing
anything from it (see ADR-0033).

Same story for `payme -.-> scheduler`: the `apps/scheduler` `payme_timeout`
job imports `payme.models`/`payments.service` directly (not `payme.api`) to
auto-cancel state-1 transactions Payme itself never followed up on after
12h, so `payme`'s timeout guarantee depends on that process running, without
`payme.api` importing anything from `scheduler` in the other direction (see
ADR-0034).

And again for `uzum -.-> scheduler`: the `apps/scheduler` `uzum_timeout` job
imports `uzum.models`/`payments.service` directly (not `uzum.api`) to
auto-fail `CREATED` transactions Uzum itself never confirmed or reversed
after 30 minutes, so `uzum`'s timeout guarantee likewise depends on that
process running, without `uzum.api` importing anything from `scheduler` in
the other direction (see ADR-0035).

And again for `click -.-> scheduler`: the `apps/scheduler` `click_timeout` job
imports `click.service`/`click.models` directly (not `click.api`) to cancel
`PREPARED` transactions Click itself never followed up with a `/complete`
call after 30 minutes, so `click`'s timeout guarantee likewise depends on
that process running, without `click.api` importing anything from
`scheduler` in the other direction (see ADR-0036).

`fulfillment -.-> worker` is the same out-of-process pattern, one direction
reversed: `apps/worker` is a thin asyncio loop (`yupay_worker.consumer`)
that imports `fulfillment.api.drain_pending_tasks` — through the module's
public interface, unlike the scheduler jobs above, which reach past
`*.api` on purpose to dodge pulling in the router stack — and calls it on
every `LISTEN fulfillment_queue` wake-up or poll tick. With
`fulfilment_async` off (the default), `fulfillment` never depends on the
worker at all: `start_for_order` runs tasks inline in the same request,
byte-identical to pre-ADR-0064 behaviour. With the flag on, `start_for_order`
only ever leaves rows `pending` and `pg_notify`s — it is the worker process
that actually executes them, so the dotted edge marks a dependency that
exists only in that mode (see [ADR-0064](../decisions/0064-postgres-fulfilment-queue.md)
and `docs/runbooks/fulfillment-queue.md`).

The `catalog <--> reviews` pair is a deliberate two-way edge, not a cycle to
break: `reviews.service` reads `catalog`'s `Brand`/`Product`/`Sku` **models**
(to resolve a brand by slug and verify the order contains it), while
`catalog.service` reads `reviews`' aggregate via `reviews.service.get_stats`
to attach `rating` to brand DTOs. To keep the storefront render path free of
an import cycle at bootstrap, `catalog.service` imports `reviews.service`
directly rather than `reviews.api` (whose `routes` would pull the whole
`api/v1` router stack) — the same trap the scheduler jobs avoid. The
`reviews -.-> scheduler` dotted edge marks the nightly `recompute_review_stats`
job, which imports `reviews.service.recompute_all_stats` directly to rebuild
`brand_rating_stats` from published reviews — a drift safety net over the
transactional bumps (see ADR-0039).

The `orders --> realtime`, `payments --> realtime`, and `fulfillment -->
realtime` edges are publish-only: each service calls
`realtime.api.publish_order_event(order.user_id, message)` right after an
order-status transition, via a **lazy, function-local import**
(`from yupay.modules.realtime import api as realtime`) rather than a
module-level one — importing at module scope would pull `realtime.routes`,
and with it the whole `api/v1` router stack, into every
`orders`/`payments`/`fulfillment` import, the same trap the scheduler jobs and
`catalog`↔`reviews` avoid above. `realtime --> core` is the Redis pub/sub
connection (`get_redis()`), not a shared table — `realtime` owns no tables of
its own. The web/miniapp frontends are WS **clients** of `realtime`'s
`/ws/orders` endpoint, an out-of-process dependency like `scheduler` rather
than a Python import, so — like `scheduler` — it is not drawn as a module edge
here (see `docs/decisions/0040-order-realtime-ws.md`).

`orders --> gifts` is a direct import: `orders.service` calls
`gifts.checkout.is_gift_sku`/`price_gift_line` to decide whether a line
needs server-side re-pricing before it's persisted. `gifts.checkout`
imports nothing from `orders`, so the edge is one-directional and no
cycle exists. `gifts --> fx` is `gifts.routes` fetching a USD→UZS rate
once per request (`fx.factory.build_default_service`) to render a display
price alongside the USD one — the same pattern `catalog --> pricing -->
fx` uses for the rest of the storefront. **`gifts`'s dependency on
G-Engine itself is not drawn as a module edge**, for the same reason a
payment gateway's dependency on its acquirer isn't: it's an external HTTP
API, not a `yupay.modules.*` import. `gifts.service` and `gifts.checkout`
build their own transient `GEngineClient` straight from settings
(`fulfillment.suppliers.gengine_client`) rather than going through
`fulfillment.api`, specifically so that importing `gifts` never pulls in
the whole `fulfillment` package — and, in the other direction,
`fulfillment` never imports `gifts` at all: the fulfilment branch for a
gift line (`fulfillment/suppliers/gengine_gifts.py`) is reached purely by
`sku_supplier_mapping.kind == "gift"`, a plain string dispatch with no
import back into this module (see
[ADR-0066](../decisions/0066-steam-gifts-live-catalog.md)).
