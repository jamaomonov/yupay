# YuPay — Module Map

Each module owns its tables and exposes a narrow Python interface via `apps/api/src/yupay/modules/<name>/api.py`. Other modules call `api.py` or react to outbox events. This is the single rule that keeps future microservice extraction a refactor rather than a rewrite.

**No cross-module SQL _writes_, and no cross-module joins on the request path's write side.** A module never `UPDATE`s or `INSERT`s into another's tables — that is the invariant, and it has no exceptions. Read-only joins into another module's tables are permitted **for a read model**, where the alternative is an N+1 across a module boundary that no amount of batching in `api.py` can fix: `merchants/price_list.py` (the B2B price list joins `brands`/`products`/`skus`), `merchants/validate.py` (the same three-table join, one row: a `sku_id` resolved to its product's form schema and to the effective B2B visibility that decides whether a merchant may check it at all), `merchants/admin.py` (merchant balances joined from `wallet_*`), `integrations/merchant_feed.py` and `admin/service.py` all do this deliberately. The extraction cost is real and accepted: each such join becomes an API call the day a module moves out, which is why they are listed here rather than left to be discovered.

| `orders`         | Order aggregate, lifecycle FSM, idempotent creation, pricing snapshot. Its `Actor` has three arms (`user_id`/`guest_email`/`merchant_id`), so `/merchant/v1` reuses `create_order` instead of forking it; idempotency is scoped per arm. `on_order_status_changed(db, order, *, publish_realtime=True)` is the **one seam** every status transition in the system goes through — this module's four sites plus `payments.service`'s four and `fulfillment.service`'s two, which used to keep three verbatim copies of the realtime nudge between them. The webhook needed the seam rather than the existing publish because `publish_order_event` is a no-op for a NULL `user_id`, which every merchant order has. `publish_realtime=False` at the two sites that deliberately have no nudge: the fulfilment settle, which emits `order.delivered` instead, and `mark_merchant_order_paid`, which has no owner to nudge. M3b Task 5 adds one column to `order_items`: `merchant_expected_price_usd`, the price a reseller said they expected to pay, frozen at order time (migration 0072, spec item 3b, ADR-0071). It is **merchant-only and read by nothing** — `expected_price` is an accept/reject tolerance and never a bid, so it decides no money — and it reaches this module the same way the wholesale price does, through a merchant-only `create_order` keyword guarded beside `unit_price_usd_override`, because `merchants` may not write another module's table. NULL therefore means _not a merchant line, or placed before 0072_, and `orders.merchant_id IS NOT NULL` is what separates those. No index: the runbook's drift sweep does filter on it, but by hand and rarely, and no code path reads it at all — and a frequent reader would want a _partial_ index over the merchant lines, not a Task 4 adds the money path: `POST /merchant/v1/orders` (`orders.py`) — one SKU, priced by `pricing`, reconciled against the caller's `expected_price` by `pricing.price_to_charge` (spec §8.4 as amended by the owner 2026-09-07, ADR-0069: the ±2% band is an accept/reject tolerance, never a bid — drift ≤ ±2% executes at **our** current price, beyond it is `422 price_changed`), floored by the same `violates_margin_floor` the catalog applies, charged to the deposit by `deposit.charge_deposit` (`C merchant_deposit / D house_payments_received`, `SELECT … FOR UPDATE` on the deposit row as the overdraw guard, ledger key `merchant-order:{order_id}`), then born **paid** and handed to fulfilment — all in one transaction. It reuses `orders.create_order` through a merchant-only `unit_price_usd_override` seam rather than forking it, is idempotent on the reseller's `merchant_order_id` and not on an `Idempotency-Key` header (spec §9.3, AGENTS §9), refuses an `affiliate_code` on the merchant arm, and never mails anyone (`notifications._delivery_recipient` returns `None` for a merchant order by an explicit guard). It is declared with Starlette's `:path` convertor because `merchant_order_id` may contain `/` (the auth README's worked example is `my%2Forder`): the segment is percent-decoded before it is matched while the signature still covers the raw request line. Scope is the authenticated merchant via `orders.find_merchant_order`, and another merchant's order answers with the byte-identical `404 order_not_found` a nonexistent id gets, so there is no oracle for a competitor's order numbering. The artifact is filtered through `fulfillment.buyer_safe_artifact`, the storefront's own allow-list, moved from `fulfillment/routes.py` to `fulfillment/service.py` so both surfaces share one list; `failure_reason` is a closed vocabulary read off the order's status and its **item**'s state — and, since M3b Task 4, off `fulfillment.stall.order_is_stalled` as well, so it is **not** a pure function of the item. The item is what inherits fulfilment's rule that a low-supplier-balance failure is not reported as a _failure_; the stall predicate is what stops it being reported as nothing at all. Precedence, because a fifth value would have to land in it: order status, then the item, then the stall — see the M3b Task 4 paragraph at the end of this cell. `GET /merchant/v1/transactions` (`transactions.py`) pages the merchant's own deposit ledger through M1's grouped query (`deposit.list_deposit_transactions`, shared with the admin panel rather than re-summed) with a **keyset** cursor on `(created_at, id)` — not OFFSET, because the ledger is written while it is read and an inserted row would make an offset page repeat a charge. M3a Task 3 adds the **producer** (`webhooks.py`): `enqueue` writes one `pending` delivery **in the caller's transaction** and issues `pg_notify('merchant_webhook_queue', <delivery_id>)` inside it, so Postgres drops both on ROLLBACK — the channel name is the single constant `WEBHOOK_QUEUE_CHANNEL`, which Task 4's listener imports rather than respells. A merchant with no hook and one with a disabled hook are the **same outcome, no row**: the outbox holds only deliverable work. The insert rides a SAVEPOINT and an `IntegrityError`/`DataError` from it is swallowed with a structured `error` line (type + SQLSTATE only — a `NotNullViolation` renders `DETAIL: Failing row contains (…)`, which would put the `url` snapshot, sized to hold a path with a token in it, into Loki), because an order is money and a webhook is a courtesy; the swallow is narrow so a broken session still propagates. `order.status_changed` carries exactly `{merchant_order_id, order_id, status, at}` and **nothing from the delivery artifact** — asserted as an exact key set, since a voucher code is a bearer instrument and a webhook body is written to the receiver's logs wholesale; `balance.credited` carries `{amount_usd, balance_usd}` as two-decimal strings through the same `machine_schemas` annotations `/merchant/v1` uses, and is skipped on a ledger **replay**, which books nothing. M3a Task 5 lands the sixth and last v1 endpoint, `POST /merchant/v1/validate/player` (`validate.py`): the storefront's own `integrations.player_check` providers (G2B nickname lookup, Waxpeer Steam login — breaker and 300 s cache included) exposed to a reseller, and deliberately **not** reimplemented. The rule is spec §9.1's "never a fake approver", which decides the shape: `player_check` folds every fault into `status="error"` rather than raising, so an outage, a timeout, a rejected credential of ours and an open circuit are one answer meaning "we learned nothing", and none of them may render as `valid`; a SKU whose product declares no checker gets a **fourth** status, `unsupported` — not `valid`, and not a 404 that would read as "no such SKU" — distinct from `error` because that one is worth retrying and this one never is. The SKU lookup is scoped exactly as `/catalog` is (`brand.visible_b2b AND sku.visible_b2b`) so it cannot enumerate withheld SKUs, and refuses with `quote.unavailable`'s own `404 item_unavailable` (`unknown_sku` / `not_b2b_visible`) rather than a second vocabulary; the order path's stock and pricing reasons deliberately do not apply, because those move between a check and an order. It is a `POST` that writes nothing and takes no `Idempotency-Key` — the end customer's identifier must stay out of the URL and therefore out of the edge access log (AGENTS §9 names it as the third such advisory lookup) — and it carries its own stricter per-IP bucket, `merchant-validate` at 120/60 s charged in the handler on top of the prefix's 600/60 s, because it is the one endpoint here that spends a supplier's quota rather than ours (spec §12). Refunds and the cabinet BFF arrive per the spec's M3b–M4 rollout. M3a Task 3 fills that outbox (`webhooks.py`: one `pending` row + a `pg_notify('merchant_webhook_queue', delivery_id)` **inside the caller's transaction**, behind a SAVEPOINT so a courtesy can never fail money) and M3a Task 4 drains it (`webhook_delivery.py` claims/signs/sends, `webhook_outcome.py` writes the row and the hook's health, `webhook_retry.py` is the pure decision table — run from `apps/worker` — see `sequence-diagrams/merchant-webhook-delivery.mmd`). The delivery half is worth four specifics. **The signature** is HMAC-SHA256 under the `ypmw_` secret over `{timestamp}\n{delivery_id}\n{event_type}\n{sha256(body)}`, sent as `X-Yupay-{Timestamp,Delivery,Event,Signature}`; the delivery id is in the **signed** material and not merely a header, because a webhook is at-least-once and a retry after a lost 200 is otherwise indistinguishable from a genuine second transition — `order.status_changed` carries no event id in its body, so this is the receiver's only dedupe handle and adding it later would be a `/merchant/v2`. **The retry table** is derived from `core/outbound_errors.py` rather than from exception names: a `RECEIVED` failure is terminal (their server has it; a retry re-delivers), a refusal is terminal (the row's `url` is a snapshot, so fixing the endpoint does not fix the row), an unreachable failure backs off 30 s doubling to 1 h with `Retry-After` honoured on 429/503 clamped to `[1 s, 1 h]`, a 4xx other than 408/429 is terminal — and `OutboundBrokenError` is the one class excluded from the failure budget, because our own bug must not auto-disable a working endpoint. **The claim** orders by `next_attempt_at, created_at, id`: both timestamps default to `CURRENT_TIMESTAMP`, which is the _transaction start_, so one placement's `paid` and `fulfilling` rows tie in both and the uuid7 id is what keeps a reseller from reading the later `paid` as a status regression; rows are then processed merchant-major so concurrent drainers take hook-row locks in one order. **The auto-disable** fires at `MERCHANT_WEBHOOK_DISABLE_AFTER_FAILURES` consecutive attempts, sets `disabled_at`, and emails every `merchant_users` operator once per disable naming the endpoint's host (not its URL — a path can carry a token); queued rows are left `pending` and unclaimed, so `PUT .../webhook` clearing `disabled_at` and the streak is the whole recovery path. M3b Task 2 fixes the defect M2 left in the deposit ledger: `refunded_usd` on the merchant order read filtered ledger transactions on `reference_type == "order"` while `credit_deposit` — the only surface that credits a deposit — referenced the **merchant**, so the field could only ever answer `"0.00"` and the hand settlement support performs after a failed delivery was invisible on the order it paid for. `POST /admin/merchants/{id}/deposit-credits` gains an optional body field `order_id` (our order id, not the reseller's `merchant_order_id`) and `deposit.credit_deposit` an `order_id=` argument: given, the posting references the order, so the amount lands in `refunded_usd` and carries the reseller's own `merchant_order_id` onto `GET /merchant/v1/transactions`; omitted, the credit is byte-for-byte the prepayment it was — same legs, same kind, same `merchant` reference, and the `balance.credited` payload untouched at `{amount_usd, balance_usd}` either way. The order must belong to the credited merchant: one that does not, one that does not exist and a string that is not a UUID answer a single `404 order_not_found` (`deposit.CODE_ORDER_NOT_FOUND`, which `order_status` now re-exports instead of respelling), because a distinguishable "not yours" is the oracle `/merchant/v1`'s reads already refuse to be and because M4's cabinet will reach the same function from a merchant-chosen id. The id is canonicalised with `str(UUID(...))` before it is compared **and** before it is stored — `orders.id` is a Postgres `uuid` (a `{braced}` .NET spelling reaching it raw is a 500) while `reference_id` is a `VARCHAR` that would store a spelling matching nothing, which is this same defect one layer down. No migration: `wallet_transactions.reference_type`/`reference_id` already exist and already hold exactly this. The reference words are now one constant each (`deposit.ORDER_REFERENCE_TYPE` / `MERCHANT_REFERENCE_TYPE`) read back through one function (`deposit.order_reference_of`, which `transactions.build` and the admin credit response share), so a writer and a reader can no longer disagree silently. M3b Task 3 makes the refund automatic: `merchants/refund.py` posts `D merchant_deposit / C house_payments_received` keyed `merchant-order-refund:{order_id}` (a namespace that cannot collide with the charge's — neither prefix is a prefix of the other, and `wallet.service.post` replays by key without comparing parameters), for the amount read off the **charge's own ledger transaction** (`deposit.charged_for_order`) rather than off the order line. The two carry one number today — `merchants.orders.place` binds `quote.price_for`'s result once and passes it to both `unit_price_usd_override` and `charge_deposit` — and nothing enforces that they stay equal, while an order with no charge posting must refund nothing rather than the price printed on its line. It fires from `fulfillment.service._settle_merchant_deposit` — a **lazy** import in both directions' honest sense: `merchants` imports `fulfillment` at module scope (`order_status.py`), so the call back is a function-local import with the reason written at it. The seam runs **outside** `drain_pending_tasks`' per-task SAVEPOINT, because that savepoint's crash arm records `MoneyOutcome.UNKNOWN`, which nothing can lower again — a refund raising inside it would turn a refundable failure permanently unrefundable. `SPENT`/`UNKNOWN` refund nothing and alert ops. The seam is called from all **four** sites that can terminally fail a merchant task — the drain, `retry_task`, `process_webhook_update` and `fail_manual_task` (reachable because a B2B-visible **`top_up`** SKU with no active `SkuSupplierMapping` and no sourcing rule falls through `sourcing._resolve_auto` to `supplier:manual`) — and its **whole body**, the lazy import and its reads included, sits inside one savepoint and one `except Exception`, because propagating out of `drain_pending_tasks` would livelock the shared fulfilment queue for retail too. Catching is safe because of where it sits: outside the per-task savepoint, so it can never reach the crash arm and never write `UNKNOWN`. Nothing is swallowed — every exception is logged with the order id and alerted, tagged `modelled=true` or `false` so an ordinary refusal and an `ImportError` from the lazy import are one query apart; the classification reads `sys.modules` rather than importing, because an `except` arm is outside its own `try` and an import there failed on exactly the case it exists to report. **Two** regions sit outside that protection and both are deliberate: the flush of the caller's own writes, which a savepoint cannot contain without discarding the failure record the refund acts on, and the handler itself, which is import-free and wrapped so a raise while reporting degrades to one bare line rather than to a stalled queue. Retail pays one indexed `merchant_id` read (`_merchant_of_task`) and neither the savepoint nor the reads, because `INVENTORY_FAILURE_MONEY_OUTCOME` is `RETURNED` and fires whenever an inventory route runs dry with nothing to fall back to (`decision.strict or decision.fallback is None` — a dry warehouse **with** a supplier fallback re-routes instead of failing) — and that read is **inside the try and outside the savepoint**, which are two different things: a fault there is reported like any other, but a transaction-poisoning one is reported and _not repaired_, since there is no savepoint to roll back to. Getting those two confused is how the gate briefly sat outside every catch. `_apply_cancel` deliberately does **not** refund — cancelling is a human action — but a cancelled merchant task logs and alerts **unless the order is already square against what it charged**, because it leaves a debited deposit on an order nothing can move again. The gate compares against the charge and not against zero (`refund.settled_in_full`, shared with `order_status._failure_reason`): a one-cent settlement is a human mid-decision, and reading that sum as a flag would have silenced the alert on the other $1.06. It exists at all because `cancel_open_tasks_for_order` also cancels `failed` tasks, so support closing an already-refunded order reaches that line on the feature's happy path. Two guards keep a refunded order from being delivered anyway (`charge_deposit` is idempotent on the order, so a second charge debits nothing): `retry_task` and `complete_manual_task(force=True)` refuse with `409 deposit_already_returned`, and `credit_deposit` refuses a hand settlement that would take an order past its own charge (`409 order_already_settled`), the two directions of the same double-credit. The manual procedure stays as the fallback — the runbook's settlement procedure is rewritten around the new field, and the admin SPA's deposit-credit form (`apps/admin/src/features/merchants/`) carries the field so the settlement's primary UI can actually produce an attributed credit: it canonicalises the id exactly as the API does (`parseOrderId` mirrors `str(UUID(...))`, braces and `urn:uuid:` included) and refuses a non-UUID **before** posting, because the API's refusal for a malformed id is deliberately the same `404` as "not this merchant's order" and would read to an operator who pasted a `merchant_order_id` as "no such order". The attribution is echoed back off the response and shares the form's existing replay-mismatch banner, since a posted attribution — unlike a wrong amount — can never be re-pointed. M3b Task 4 makes the one **non-terminal** failure visible: a supplier that refuses for lack of _our_ balance fails the task while deliberately leaving the item `in_progress` (retail's rule, so the storefront keeps saying "обработка"), which left a merchant order publishing `status: "fulfilling", failure_reason: null` — byte for byte what an order placed thirty seconds ago publishes — indefinitely. `order_status` now answers `fulfillment_delayed`: the delivery has stopped, the order has not, keep polling and do not refund your end customer. It is **derived, never stored** (`fulfillment.stall.order_is_stalled`: a task in `failed` whose order item is still open), because a stored marker would have to be cleared at every route out of a stall — the top-up retry, a terminal retry, a cancel, a manual delivery, a hand closure — and the site that forgot would publish "still coming" about a finished order. It comes **last** in the precedence, after `order_failed` and the failed-item split, because those are endings and this one is not. It never names its cause, for the same reason `SPENT` and `UNKNOWN` are not distinguishable here, and it pushes nothing: a stall moves neither money nor `orders.status`, so there is no webhook and the poll is the whole mechanism. The two published statements it falsified — "treat a non-null `failure_reason` as terminal" and the worked polling loop that broke on `failure_reason != null` — were repaired in the same commit, because a loop copied from our own README would have stopped polling an order we were about to deliver. No migration and no new write site: the read costs one indexed lookup on `ix_fulfillment_tasks_order_id`, and only while the order is still open. M3b Task 5 writes the milestone down — **ADR-0071** carries the decisions (the three-valued outcome and why an unknown never auto-refunds, which adapter mapping is a field, which is a sentence in a vendor's documentation, and which is a supplier's error string plus an owner's ruling that it is not billed (M3c: `g2b`'s invalid-player rejection, the one thing that adapter auto-refunds **after** a call has gone out), why the posting references the order, the key that must not collide, the monotone ladder and the fact that **no operator re-grade path exists in either direction**), and `sequence-diagrams/merchant-refund.mmd` carries the path. It also closes spec item 3b, and closes it by halves: the _computed list price_ needed no column — `merchants.orders.place` binds `quote.price_for`'s result once and hands the same value to `unit_price_usd_override` and to `charge_deposit`, so `order_items.unit_price_usd` **is** that price and a second column would be filled from the same expression, turning the runbook's regression query into a comparison of a value with itself — while the merchant's own `expected_price` was genuinely unrecorded, surviving only inside `_request_digest`'s one-way SHA-256. | `fulfillment`    | Saga orchestrator (reserve → pay → fulfill → deliver, with compensations). `fulfillment_tasks` doubles as a Postgres-native work queue behind the `fulfilment_async` flag: `start_for_order` leaves tasks `pending` and rides a `pg_notify('fulfillment_queue', order_id)` on the same commit instead of running them inline; the separate `apps/worker` process drains them via `drain_pending_tasks` (`FOR UPDATE SKIP LOCKED`), woken by `LISTEN` with a poll-tick fallback. Replaces the never-used Dramatiq entrypoint (ADR-0064). Its `fulfilling` and `delivered` transitions — the two events a reseller actually waits for — route through `orders.service.on_order_status_changed`, the status-change seam, rather than through a local copy of the realtime nudge. A terminal failure does **not** route through it — nothing advances `orders.status` — which is why M3b Task 3's automatic merchant refund is announced by `balance.credited` (a deposit credit like any other) while the order's own state is only ever polled. M3b Task 4 adds `stall.py`, a read-only leaf beside the saga: `order_is_stalled(order)` answers whether a task of this order has stopped (`status = 'failed'`) while the item it was fulfilling has not, which is the shape `_apply_failure`'s low-balance early return produces and the one soft failure this module has. It matches the **shape**, not `last_error == 'supplier_low_balance'`: five of the six sites that fail a task also fail its item in the same breath, so the sentinel and the shape have one producer each today, and a second soft failure added later is still a stall. Nothing in the saga writes anything for it — `merchants.order_status` is the only caller, and the fact stays derived so no exit from a stall has a marker to clear. Cycles are prohibited. When a "downstream" module needs to influence an "upstream" one, it does
so by emitting an event consumed by the upstream module's handler — not by importing it.

`core` is not on that graph because everything depends on it and it depends on
nothing (`core/__init__.py` states the rule). Two of its members are worth
naming here anyway, because they are policy rather than plumbing:
`core/outbound.py` — the only outbound fetcher allowed to take a URL a third
party chose, which re-checks the resolved address at connect time — and
`core/outbound_addresses.py`, whose `BLOCKED_FAMILIES` is the single
blocked-range table in the repo (`catalog/image_url_safety.py` classifies its
save-time literals through it rather than keeping a second list). The
taxonomy `apps/worker`'s delivery drain branches on is
`core/outbound_errors.py` — three-valued `Delivery` plus a two-wide family,
which `merchants/webhook_retry.py` reads _as data_ to build its retry table
rather than matching on class names; the destination parsing is
`core/outbound_target.py`. `OutboundResponse` carries exactly one response
header, `Retry-After`, because a retry policy that ignores a 429's own answer
to "when should I come back" is hammering a server that asked it not to.

`scheduler` (dotted edge above) is not a `yupay.modules.*` package — it's the
separate `apps/scheduler` process. The dotted line marks it as an
out-of-process dependency rather than a Python import: the `broadcast_dispatch`
job reads/writes `broadcasts`' own tables directly and calls the
`notifications` Telegram channel itself, so `broadcasts`' delivery path
depends on that process running, without `broadcasts.api` ever importing
anything from it (see ADR-0033).

Same story for `payme -.-> scheduler`: the `apps/scheduler` `payme_timeout`
job imports `payme.models`/`payments.service` directly (not `payme.api`) to
auto-cancel state-1 transactions Payme itself never followed up on after
12h, so `payme`'s timeout guarantee depends on that process running, without
`payme.api` importing anything from `scheduler` in the other direction (see
ADR-0034).

And again for `uzum -.-> scheduler`: the `apps/scheduler` `uzum_timeout` job
imports `uzum.models`/`payments.service` directly (not `uzum.api`) to
auto-fail `CREATED` transactions Uzum itself never confirmed or reversed
after 30 minutes, so `uzum`'s timeout guarantee likewise depends on that
process running, without `uzum.api` importing anything from `scheduler` in
the other direction (see ADR-0035).

And again for `click -.-> scheduler`: the `apps/scheduler` `click_timeout` job
imports `click.service`/`click.models` directly (not `click.api`) to cancel
`PREPARED` transactions Click itself never followed up with a `/complete`
call after 30 minutes, so `click`'s timeout guarantee likewise depends on
that process running, without `click.api` importing anything from
`scheduler` in the other direction (see ADR-0036).

`merchants -.-> worker` is the second edge of that shape and is **not drawn**
above, because `merchants` has no node on the graph at all. It is the same
dependency: `apps/worker` imports `merchants.api.drain_pending_deliveries` and
`merchants.api.WEBHOOK_QUEUE_CHANNEL` — through the facade, like the fulfilment
one — and drains `merchant_webhook_deliveries` on every wake. Unlike fulfilment
there is no flag: the producer always writes rows, so a webhook a merchant
configured is delivered only if this process is running. `yupay_worker.Queue`
(name, channel, drain, concurrency) is what makes the loop carry two queues
rather than two copies of itself, and each queue runs in its **own task** — a
`gather` across both returns with its slowest member, which would have made a
slow merchant endpoint the fulfilment queue's polling period. A NOTIFY on
either channel still wakes both (an empty queue costs one indexed query), but
each queue owns its own event, because one shared event between two consumers
is a lost wake-up.

`fulfillment -.-> worker` is the same out-of-process pattern, one direction
reversed: `apps/worker` is a thin asyncio loop (`yupay_worker.consumer`)
that imports `fulfillment.api.drain_pending_tasks` — through the module's
public interface, unlike the scheduler jobs above, which reach past
`*.api` on purpose to dodge pulling in the router stack — and calls it on
every `LISTEN fulfillment_queue` wake-up or poll tick. With
`fulfilment_async` off (the default), `fulfillment` never depends on the
worker at all: `start_for_order` runs tasks inline in the same request,
byte-identical to pre-ADR-0064 behaviour. With the flag on, `start_for_order`
only ever leaves rows `pending` and `pg_notify`s — it is the worker process
that actually executes them, so the dotted edge marks a dependency that
exists only in that mode (see [ADR-0064](../decisions/0064-postgres-fulfilment-queue.md)
and `docs/runbooks/fulfillment-queue.md`).

The `catalog <--> reviews` pair is a deliberate two-way edge, not a cycle to
break: `reviews.service` reads `catalog`'s `Brand`/`Product`/`Sku` **models**
(to resolve a brand by slug and verify the order contains it), while
`catalog.service` reads `reviews`' aggregate via `reviews.service.get_stats`
to attach `rating` to brand DTOs. To keep the storefront render path free of
an import cycle at bootstrap, `catalog.service` imports `reviews.service`
directly rather than `reviews.api` (whose `routes` would pull the whole
`api/v1` router stack) — the same trap the scheduler jobs avoid. The
`reviews -.-> scheduler` dotted edge marks the nightly `recompute_review_stats`
job, which imports `reviews.service.recompute_all_stats` directly to rebuild
`brand_rating_stats` from published reviews — a drift safety net over the
transactional bumps (see ADR-0039).

The `orders --> realtime`, `payments --> realtime`, and `fulfillment -->
realtime` edges are publish-only: each service calls
`realtime.api.publish_order_event(order.user_id, message)` right after an
order-status transition, via a **lazy, function-local import**
(`from yupay.modules.realtime import api as realtime`) rather than a
module-level one — importing at module scope would pull `realtime.routes`,
and with it the whole `api/v1` router stack, into every
`orders`/`payments`/`fulfillment` import, the same trap the scheduler jobs and
`catalog`↔`reviews` avoid above. `realtime --> core` is the Redis pub/sub
connection (`get_redis()`), not a shared table — `realtime` owns no tables of
its own. The web/miniapp frontends are WS **clients** of `realtime`'s
`/ws/orders` endpoint, an out-of-process dependency like `scheduler` rather
than a Python import, so — like `scheduler` — it is not drawn as a module edge
here (see `docs/decisions/0040-order-realtime-ws.md`).

`orders --> gifts` is a direct import: `orders.service` calls
`gifts.checkout.is_gift_sku`/`price_gift_line` to decide whether a line
needs server-side re-pricing before it's persisted. `gifts.checkout`
imports nothing from `orders`, so the edge is one-directional and no
cycle exists. `gifts --> fx` is `gifts.routes` fetching a USD→UZS rate
once per request (`fx.factory.build_default_service`) to render a display
price alongside the USD one — the same pattern `catalog --> pricing -->
fx` uses for the rest of the storefront. **`gifts`'s dependency on
G-Engine itself is not drawn as a module edge**, for the same reason a
payment gateway's dependency on its acquirer isn't: it's an external HTTP
API, not a `yupay.modules.*` import. `gifts.service` and `gifts.checkout`
build their own transient `GEngineClient` straight from settings
(`fulfillment.suppliers.gengine_client`) rather than going through
`fulfillment.api`, specifically so that importing `gifts` never pulls in
the whole `fulfillment` package — and, in the other direction,
`fulfillment` never imports `gifts` at all: the fulfilment branch for a
gift line (`fulfillment/suppliers/gengine_gifts.py`) is reached purely by
`sku_supplier_mapping.kind == "gift"`, a plain string dispatch with no
import back into this module (see
[ADR-0066](../decisions/0066-steam-gifts-live-catalog.md)).
