# 0109. API на трёх процессах uvicorn

- **Status**: Accepted (2026-11-25)
- **Date**: 2026-11-25
- **Deciders**: владелец
- **Tags**: backend | infra

## Context and problem statement

Прод-API — один процесс `uvicorn` без `--workers`: один event loop на одном ядре и один пул
SQLAlchemy (10 + 10). На сервере 8 ядер. 2026-11-25 `ApiHighLatency` срабатывал каждые
10–40 минут: сайт при перегенерации страниц регионов за минуту запрашивал ~280 брендов и
~280 продуктов. Один такой запрос стоит ~40 мс CPU, поэтому 10 запросов в секунду занимали
ядро целиком, p95 рос до 2–9 с, а оплата, кабинет реселлера и проверка игрока стояли в той же
очереди. Ограничение на стороне сайта (`createGate`) снимает этот конкретный всплеск, но
следующий (поисковый бот, рекламная кампания) снова упрётся в одно ядро. Владелец записал это
как долг и в тот же день сказал: «го долг по процессам сделаем».

## Decision

- `WEB_CONCURRENCY=3` у сервиса `api` в `docker-compose.prod.yml`: uvicorn берёт из этой
  переменной значение `--workers` по умолчанию, поэтому образ и `CMD` не меняются, а dev и
  тесты остаются на одном процессе. Супервизор uvicorn перезапускает упавший воркер.
- **Метрики** — режим multiprocess у `prometheus_client`: `PROMETHEUS_MULTIPROC_DIR=/run/prometheus`
  на tmpfs, чтобы каждый старт контейнера начинался с пустого каталога. `GET /metrics` теперь
  отдаёт `core/metrics_export.py`, а не `Instrumentator.expose`: скрейп суммирует файлы всех
  воркеров. Метрики `process_*` (CPU, fds, память) в этом режиме пропадают, поэтому
  `WorkerProcessCollector` отдаёт их по каждому Python-процессу контейнера с меткой `pid`.
  Выражения `ApiSaturated` и `ApiFileDescriptorsHigh` не меняются и теперь срабатывают на
  любой отдельный воркер. Метка ограничена: это супервизор и N воркеров, а `pid` меняется
  только при перезапуске воркера.
- **Память**: `mem_limit` api 2g → 3g. Три воркера по ~370 МБ плюс argon2: у каждого
  процесса свой `PASSWORD_LIMITER(4)` по 64 МиБ, итого в худшем случае ~1,9 ГБ.
- **База**: пулы теперь могут взять 140 соединений (api 3 × 20 + worker 2 × 20 + scheduler 20 +
  bot 20) из `max_connections=200`.

## Состояние внутри процесса

Проверено перед решением:

- брейкеры, кэши, бюджеты Waxpeer и csmarket, `ip_guard` живут в Redis;
- WebSocket: у каждого соединения своя подписка в Redis pub/sub;
- фоновые `create_task` (алерты, уведомления, пересборка прайса реселлера) не требуют
  единственного процесса.

Одно ослабление, принятое заранее: `slowapi` хранит счётчики в памяти процесса
(ADR-0028), поэтому грубый лимит по IP становится до 3× номинала. Это внешний предохранитель;
точные лимиты (`ip_guard`, merchant guard) живут в Redis и не меняются.

## Consequences

- Всплеск занимает одно ядро из трёх, остальные воркеры продолжают обслуживать запросы.
- Скрейп `/metrics` читает файлы с tmpfs. Файлы воркеров, которые умерли и перезапустились,
  остаются в каталоге и продолжают суммироваться до рестарта контейнера: для счётчиков и
  гистограмм так и надо, а gauge в API нет.
- Откат: убрать `WEB_CONCURRENCY` (или поставить `"1"`) и выполнить `up -d api` с
  `IMAGE_TAG`. Каталог метрик работает и с одним процессом.
