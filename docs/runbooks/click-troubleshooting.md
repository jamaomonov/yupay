# Runbook — Click Shop API troubleshooting

Click (`click.uz`) is the fourth acquirer, behind the "Click" payment method
on both the web storefront (provider slug `click`) and the Telegram mini app
(provider slug `click_miniapp`). Like Payme and Uzum, Click does not deliver a
webhook to us — **we run two plain HTTP endpoints** that Click calls over the
life of each transaction, at `POST /api/v1/payments/click/{prepare,complete}`.
We own the transaction state machine (`ClickTransaction.status`); Click signs
every call with an MD5 `sign_string` rather than HTTP Basic auth, and — unlike
every other endpoint in this codebase — the body is
`application/x-www-form-urlencoded`, not JSON. See
[ADR-0036](../decisions/0036-click-shop-api.md) and
`apps/api/src/yupay/modules/click/README.md` for the full endpoint/error
reference.

## Quick checks

- **"Click" is missing / disabled.** The gateway is `available` (per surface)
  only when `CLICK_MERCHANT_ID` **and** that surface's own service id
  (`CLICK_SERVICE_ID_WEB` or `CLICK_SERVICE_ID_BOT`) **and** its secret
  (`CLICK_SECRET_KEY_WEB` or `CLICK_SECRET_KEY_BOT`) are all set. Confirm with
  `GET /api/v1/payments/providers` — `click` (web) and/or `click_miniapp`
  (bot) should be in the list, independently.
- **Config.** `CLICK_MERCHANT_ID` (shared, `63276`), `CLICK_SERVICE_ID_WEB`
  (`108149`) / `CLICK_SECRET_KEY_WEB`, `CLICK_SERVICE_ID_BOT` (`108150`) /
  `CLICK_SECRET_KEY_BOT`, `CLICK_MERCHANT_USER_ID_WEB` (`88645`) /
  `CLICK_MERCHANT_USER_ID_BOT` (`88644`, reference only — not read by the
  module's logic), `CLICK_PAY_URL` (default
  `https://my.click.uz/services/pay`). `CLICK_SECRET_KEY_WEB`/
  `CLICK_SECRET_KEY_BOT` are redacted from logs — never paste them into a
  ticket or chat.
- **The endpoints always answer HTTP 200.** A Click-side "connection error"
  report almost never means our route 500'd — it means Click couldn't reach
  us at all (tunnel down, DNS, Caddy), or the body couldn't even be parsed as
  form data. Check the access log for the request first; if it's not there,
  it's a reachability problem, not an application error. Every outcome —
  success or business error — is rendered as `{"error": ..., "error_note":
...}` at HTTP 200; the only exception is a stray non-`POST` request, which
  is answered `-8` at HTTP 200, never a 405.
- **The body is form-encoded, not JSON.** If Click (or a proxy in front of
  it) ever sends `Content-Type: application/json`, every field read comes
  back empty and the request is rejected with `-8` — this shows up as "every
  single call fails immediately," not a subtler signature issue. Confirm the
  raw `Content-Type` header in the access log before assuming it's a
  sign-check problem.

## The two services, one merchant

Click gave us **two independent services sharing one merchant**:

| Surface          | `service_id` | Secret                 | Backing provider slug |
| ---------------- | ------------ | ---------------------- | --------------------- |
| web (`yupay.uz`) | `108149`     | `CLICK_SECRET_KEY_WEB` | `click`               |
| bot (mini app)   | `108150`     | `CLICK_SECRET_KEY_BOT` | `click_miniapp`       |

The inbound `service_id` field on **every** Prepare/Complete request
determines both which secret verifies the signature and which `payments`
provider the backing payment is recorded under — this is independent of
which surface actually initiated the checkout link. A `service_id` that
matches neither configured id (or matches one whose secret is blank) is
treated as unauthorized: `-1`, same as a bad signature.

## Sandbox setup

1. Confirm Click has provisioned the two services (`108149`/`108150`) against
   our merchant (`63276`) and issued a `SECRET_KEY` per service — these come
   from Click, not generated by us (contrast Uzum, where we generate sandbox
   credentials ourselves).
2. Point our endpoint at a publicly reachable host — a tunnel
   (cloudflared/ngrok) in dev, or the deployed staging host.
3. Set `CLICK_MERCHANT_ID`, `CLICK_SERVICE_ID_WEB`/`CLICK_SECRET_KEY_WEB`,
   `CLICK_SERVICE_ID_BOT`/`CLICK_SECRET_KEY_BOT` in the env.
4. Hand Click's integration engineer:
   - **Callback base URL:** `https://<our-host>/api/v1/payments/click`
     (endpoints `/prepare` `/complete`).
   - **Both `service_id`s** (`108149` web, `108150` bot) — Click's sandbox
     tester needs to exercise each independently.
5. Run a real test payment through `my.click.uz/services/pay` per surface —
   web first, then the mini app (`openExternalLink`) — and confirm both
   `/prepare` then `/complete` land, in that order, for each.
6. All checks passing on both surfaces is the sandbox-ready milestone — do
   not go live before this is confirmed with Click.

## Go-live switch

1. Obtain the **production** `SECRET_KEY` for each service from Click (if
   different from sandbox — confirm with Click's engineer).
2. Set `CLICK_SECRET_KEY_WEB`/`CLICK_SECRET_KEY_BOT` to the production
   values; `CLICK_MERCHANT_ID`/`CLICK_SERVICE_ID_WEB`/`CLICK_SERVICE_ID_BOT`
   are typically unchanged between sandbox and production for Click (the
   service ids themselves don't usually flip) — confirm this with Click
   rather than assuming.
3. There is no Caddy IP allowlist configured for this path yet — the MD5
   signature is the only gate (design spec §16 gap #6; same open question as
   Uzum's unconfirmed source IPs).

## Reading a stuck transaction

Every Click transaction is one `click_transactions` row, keyed by
`(click_trans_id, service_id)` for Prepare lookups and by the
`merchant_prepare_id` we issued for Complete lookups.

1. Find the transaction. There is no admin list endpoint for
   `click_transactions` directly; cross-reference via the order or payment:
   ```
   GET /api/v1/admin/payments?order_id=<order_id>
   ```
   Check the payment's `provider` column (`click` or `click_miniapp`) to see
   which surface it's for — don't rely on the `external_id` prefix alone: a
   payment created at checkout-intent time always gets `external_id =
"click:<order_id>"` from the gateway regardless of surface, while one
   created directly by Click's own `/prepare` call (no prior intent row) gets
   `"<provider>:<order_id>"` from `click.service._ensure_payment`. `provider`
   is always correct either way; `external_id`'s prefix is not a reliable
   surface indicator.
2. **`status` meanings**: `PREPARED` (Click registered the transaction, buyer
   hasn't finished paying, or Click hasn't called `/complete` yet),
   `CONFIRMED` (order should be `paid`, fulfilment started), `CANCELLED`
   (either a negative-inbound-`error` request, or the 30-minute stale-prepare
   sweep — no money was ever settled for this transaction; see below to tell
   which).
3. **Order stuck in `pending_payment` with a `PREPARED` transaction older
   than 30 minutes**: the stale-prepare sweep (below) should have cancelled
   it. If it hasn't after several sweep intervals, check the scheduler logs
   for `click_timeout.transaction_failed` with that transaction's
   `merchant_prepare_id`.

## Sign-check debugging (`-1`)

`-1` (`SIGN CHECK FAILED!`) means either the `service_id` didn't match a
configured, fully-set-up service, or the computed MD5 didn't match the
`sign_string` Click sent.

1. **Confirm `service_id` resolves to a secret at all.**
   `signature.secret_for_service(service_id)` returns `None` — and thus `-1`
   — when `service_id` matches neither `CLICK_SERVICE_ID_WEB` nor
   `CLICK_SERVICE_ID_BOT`, **or** when it matches one but that service's
   secret (`CLICK_SECRET_KEY_WEB`/`CLICK_SECRET_KEY_BOT`) is blank. A `-1` on
   every single call from one surface (not just malformed ones) usually
   means that surface's secret is still unset post-deploy.
2. **Confirm which secret should apply.** `108149` → `CLICK_SECRET_KEY_WEB`;
   `108150` → `CLICK_SECRET_KEY_BOT`. Don't debug against the wrong secret —
   the two are independent per Click's own provisioning.
3. **The hash is built over the RAW wire strings, not reformatted values.**
   `signature.py`'s `prepare_sign`/`complete_sign` concatenate the exact
   string values Click sent — `click_trans_id`, `service_id`,
   `merchant_trans_id`, `amount` (Click's own formatting, e.g. `"1000.00"`),
   `action`, `sign_time` — **before** any int/Decimal parsing. If a
   `sign_string` mismatch is suspected, reproduce the hash by hand from the
   _exact_ raw form body (check the access log for the literal bytes), not
   from a value you've re-typed or reformatted — even changing `"1000.00"`
   to `"1000.0"` produces a different MD5.
   - Prepare formula:
     `md5(click_trans_id + service_id + secret + merchant_trans_id + amount + action + sign_time)`
   - Complete formula: same, with `merchant_prepare_id` inserted immediately
     after `merchant_trans_id`.
4. **The comparison is case-insensitive and strips whitespace on the
   received value**, but is otherwise exact — a truncated or subtly
   corrupted `sign_string` (e.g. a proxy re-encoding the form body) still
   fails. `verify()` fails closed (`False`, i.e. `-1`) on non-ASCII input
   rather than raising, so a `-1` can also mean Click (or something between
   us and Click) sent a corrupted `sign_string`, not necessarily a secret
   mismatch — rule out reachability/encoding issues before assuming the
   secret itself is wrong.
5. **Never debug by logging the secrets.** `CLICK_SECRET_KEY_WEB`/
   `CLICK_SECRET_KEY_BOT` are redacted by the structured logger (`make logs
service=api` shows `[REDACTED]`, not the value) — verify by checking the
   env file directly, never by adding a temporary log line that prints the
   raw secret.

## The negative-inbound-`error` / `-9` rule

Click's own contract: if the **request itself** carries a negative `error`
field (Click aborted the payment on its side), we must cancel our side and
answer `-9` — regardless of what state the transaction/order is otherwise in.
This is checked **before** any order-state or amount validation on both
`/prepare` and `/complete`.

- On `/prepare`, the lookup is by `(click_trans_id, service_id)` (no
  `merchant_prepare_id` exists from Click's point of view yet at this stage).
- On `/complete`, the lookup is by `merchant_prepare_id`.
- `service.cancel()` is a no-op if there's nothing to cancel, or the row is
  already `CANCELLED`. It **never** touches an already-`CONFIRMED`
  transaction's status or payment — Click v1 has no merchant-initiated
  reversal, so a settled transaction is left alone even if a later request
  for the same identifiers carries a negative `error`.
- **Money-safety invariant:** the backing payment is only ever cancel-pended
  if it is still `status == "pending"` at the moment `cancel()` runs. A
  customer retrying checkout on the same surface can share one pending
  payment across several `PREPARED` rows (`_ensure_payment` reuse) — if a
  _sibling_ transaction already confirmed that payment (order → `paid`)
  while this one is still `PREPARED`, cancelling this row never claws that
  money back. Seeing a payment move from `succeeded` back to `cancelled` here
  would be a bug, not expected behaviour — escalate immediately.

## The 30-minute stale-prepare sweep

`apps/scheduler/src/yupay_scheduler/jobs/click_timeout.py` runs every 5
minutes and cancels any `PREPARED` transaction whose `prepare_time` is older
than `TIMEOUT` (30 minutes, a default — Click's own expected window is
unconfirmed; see ADR-0036's documentation gaps). This is the dead-letter
case for a buyer who opened `my.click.uz` and abandoned it, or whose
`/complete` callback never arrived at all. Every stale row is routed through
the same `click.service.cancel()` helper the negative-`error` webhook path
uses (keyed by `merchant_prepare_id`) — re-checked `FOR UPDATE` immediately
before writing, so a concurrent `/complete` that lands between the listing
query and this tick's write is never clobbered; only a still-`PREPARED` row
at write time is touched. The same pending-payment money-safety guard
described above applies here too.

**Log lines to watch:**

- `click_timeout.tick` — one per scheduler run, with `checked` / `cancelled`
  / `errored` counts. `checked: 0` most ticks is normal (no stale backlog); a
  persistently large `checked` count with a growing `errored` count means
  something is wrong with the sweep itself (DB connectivity, a bad row
  shape) and needs investigation.
- `click_timeout.transaction_failed` — one per row the sweep could not
  cancel cleanly, with `merchant_prepare_id` and `error` (never
  account/key/PII). A transaction stuck past 30 minutes with no
  corresponding `transaction_failed` log line but also no `CANCELLED` status
  is a sign the scheduler process itself isn't running — check it's up
  before debugging individual rows.
- `click.webhook.internal_error` / `click.webhook.rollback_failed` — from the
  webhook routes, not the scheduler; logged whenever a `/prepare` or
  `/complete` call hit an unexpected exception (rendered to Click as `-7` at
  HTTP 200 regardless), keyed by `endpoint`. Check these first if Click
  reports a transaction "stuck" in a way the timeout sweep wouldn't explain
  (e.g. a `/complete` that should have succeeded).

**Money-safety invariant:** this job only ever cancels a `PREPARED`
transaction whose _payment_ is still `pending`. If you ever see a
`CONFIRMED` transaction move to `CANCELLED`, or a `succeeded` payment move to
`cancelled`, that is a bug, not expected sweep behaviour — escalate
immediately rather than assuming it's the sweep's normal operation.

## Error codes — what they mean to an operator

| Code | Operator-facing meaning                                                                                                              | Action                                                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `0`  | Success                                                                                                                              | No action                                                                                                                            |
| `-1` | Signature check failed, or `service_id` doesn't resolve to a configured secret                                                       | See "Sign-check debugging" above                                                                                                     |
| `-2` | `amount` Click sent doesn't match the order's (`/prepare`) or transaction's (`/complete`) recorded amount                            | Usually a stale checkout link (order price changed) or a sandbox test with a mismatched amount; ask the customer to restart checkout |
| `-3` | `action` field wasn't `0` (on `/prepare`) or `1` (on `/complete`)                                                                    | Should never happen from Click itself; check for a misconfigured/stray caller                                                        |
| `-4` | Order already paid (`/prepare`) or transaction already confirmed — a replay (`/complete`)                                            | Harmless — Click's own retry/idempotency signal; confirm via the order/payment that it's actually settled                            |
| `-5` | `merchant_trans_id` doesn't match any order (`/prepare` only)                                                                        | Checkout link/params was malformed, or the order was deleted                                                                         |
| `-6` | `merchant_prepare_id` unknown, or mismatched `click_trans_id`/`service_id`/`order_id` (`/complete` only)                             | Check reachability — did the corresponding `/prepare` actually land and commit?                                                      |
| `-7` | Unexpected internal error while handling the request, or a commit failure                                                            | Check API logs for `click.webhook.internal_error` with a stack trace, keyed by `endpoint`                                            |
| `-8` | Malformed request — a required field was missing/empty/unparseable, the body wasn't valid form data, or a non-`POST` method was used | Check the raw body/method in the access log against the expected shape for that endpoint                                             |
| `-9` | Order not payable (cancelled/expired/refunded), transaction already cancelled, or Click sent a negative inbound `error`              | See "The negative-inbound-error / -9 rule" above; verify the order's actual status                                                   |

## Auth vs. non-`POST` requests

Unlike Uzum, Click's catalogue has **no dedicated "wrong HTTP method" code**.
A stray `GET`/`PUT`/`PATCH`/`DELETE`/`HEAD`/`OPTIONS` on either endpoint is
answered `-8` ("Error in request from click") at HTTP 200 — the closest
semantic fit for "this wasn't a valid Click webhook call at all," not a 405.
This should never happen from Click itself; if you see it in the logs, check
for a stray health-checker or a misconfigured monitoring probe hitting the
payments path.
