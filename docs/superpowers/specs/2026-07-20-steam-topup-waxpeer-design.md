# Пополнение Steam по логину через Waxpeer

**Дата:** 2026-07-20
**Статус:** согласовано, готово к плану реализации

## Задача

Продавать пополнение кошелька Steam: покупатель вводит свой Steam-логин и сумму
в долларах, видит цену в сумах и платит привычными способами. Поставщик —
Waxpeer.

Это первый товар с **произвольной суммой**: весь каталог до сих пор состоял из
фиксированных номиналов (60 UC, 325 UC), где цена лежит на SKU.

## Контракт Waxpeer

Снят с их OpenAPI (`https://api.waxpeer.com/docs/json`), не с письма — в письме
не было статусов и комиссии.

```
GET  /v1/steam-topup/validate?steam_login=&api=   → { success, valid, msg }
POST /v1/steam-topup?api=                          → { success, msg, topup }
     body: { steam_login, amount, custom_id? }
GET  /v1/steam-topup?id=|custom_id=&api=           → { success, msg, topup }
GET  /v1/user?api=                                 → баланс аккаунта
```

Объект `topup`: `id`, `custom_id`, `status`, `amount`, `give_amount`,
`steam_login`, `created`, `updated`.

Существенное:

- **`amount` — брутто, списывается с нашего баланса.** Единица `1000 = $1`,
  значит цент = 10 единиц: суммы с двумя знаками представимы точно.
- **`give_amount` — нетто, сколько реально дойдёт до кошелька Steam.**
  В примере из документации `5000 → 4750`, то есть комиссия заложена в API.
  **На сегодня комиссия 0%** (подтверждено владельцем), но может появиться.
- Лимиты: $1–$300 на одно пополнение.
- `custom_id` (A-Za-z0-9\_-, ≤50) уникален и идемпотентен: повтор с тем же
  значением возвращает существующее пополнение, а не списывает второй раз.
- Статусы: `created` / `sending` — в полёте; `completed` — зачислено;
  `canceled` — не удалось, **деньги возвращены** на наш баланс; `error` —
  не удалось неоднозначно, **автовозврата нет**, нужна поддержка.

## Решения

### Сумма — то, что получит покупатель

Клиент вводит «$10» и получает $10 в кошельке Steam. Брутто считаем мы:
`gross = amount / (1 - fee)`, где `fee` — настройка, сейчас `0`.

**Округление — всегда вверх, до единицы Waxpeer** (цент = 10 единиц). Разница
не больше цента и всегда в пользу покупателя: получить меньше обещанного он не
должен ни при каком округлении.

Альтернатива («$10 — сколько мы отправим, дойдёт меньше») отвергнута: она
экономит нам арифметику ценой жалоб «заплатил за 10, пришло 9.50».

**Сверка после создания.** `give_amount` из ответа сравниваем с обещанным. Если
однажды окажется меньше — это расхождение фиксируем и уведомляем, а не выдаём
молча меньше обещанного. Так появление комиссии будет замечено сразу.

### Цена — рыночный курс × множитель

```
курс_витрины = проверенный_рыночный_курс(USD→UZS) × sku.rate_multiplier
цена_UZS     = сумма_USD × курс_витрины
```

Маржа зашита в курс. Покупателю показываем «1 $ = 14 025 сум» и 0% комиссии —
как принято на этом рынке.

Множитель живёт **на SKU**, а не в глобальных настройках: у следующего товара с
плавающей суммой (PSN и т. п.) будет своя маржа. Меняется из админки без
деплоя.

### Шлюз доверия к курсу

Автоматический курс без проверок — способ потерять деньги тихо. Сегодня FX
умеет: цепочку провайдеров, кэш, откат на устаревшее значение и отсев
`rate <= 0` внутри провайдеров. Чего **нет** — защиты от правдоподобного, но
неверного курса: значение вдвое ниже реального пройдёт насквозь, и мы применим
к нему множитель и продолжим продавать.

Перед использованием курс проходит проверки:

| Проверка           | Условие                                                                                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Положительность    | `rate > 0`                                                                                                                                     |
| Свежесть           | не старше `STEAM_FX_MAX_AGE` (по умолчанию 6 ч)                                                                                                |
| Отклонение         | не дальше `STEAM_FX_MAX_DEVIATION_PCT` от последнего годного (по умолчанию 15%)                                                                |
| Абсолютный коридор | в пределах `STEAM_FX_MIN_RATE`…`STEAM_FX_MAX_RATE` (по умолчанию 8 000…25 000 сум за доллар — грубая отсечка бессмыслицы, не рыночный прогноз) |

Любая непройденная проверка → **товар недоступен к покупке + алерт админу**.
Падаем закрыто: не продать хуже, чем продать вдвое дешевле себестоимости.

Пороги — в конфиге (меняются редко). Множитель — в админке (меняется часто).

### Модель каталога

Бренд **Steam** → продукт «Пополнение кошелька» (`kind = top_up`) → один SKU с
новыми полями:

| Поле                                | Смысл                       |
| ----------------------------------- | --------------------------- |
| `variable_amount: bool`             | сумму задаёт покупатель     |
| `min_amount_usd` / `max_amount_usd` | границы, `1.00` и `300.00`  |
| `rate_multiplier: Decimal`          | наша маржа, например `1.08` |

`price_usd` для такого SKU не используется — цену определяет сумма × курс.

Логин описывается обычным `required_fields` с `check: {provider: "waxpeer"}` —
и проверка логина достаётся от уже готового контрола проверки игрового ID.
Фронт не меняется.

Отвергнутые варианты:

- **Сумма как `qty`** (SKU «Steam $1», $37 = 37 штук). Не требует миграции, но
  запрещает копейки, показывает «37 × Steam $1» в истории и админке и всё равно
  требует отдельного пути ценообразования — то есть не экономит ничего.
- **Отдельный модуль вне каталога.** Полная свобода ценой дублирования заказов,
  платежей, выдачи и истории; покупка выпала бы из общего списка заказов.

### Оформление заказа

1. Клиент присылает сумму и логин.
2. **Сервер пересчитывает цену сам.** Присланной цене не верим никогда.
3. Валидация: сумма в пределах min/max, не больше двух знаков после запятой.
4. Предполётная проверка баланса Waxpeer — не берём деньги за то, что не сможем
   выдать (так же, как проверяем доступность шлюза перед созданием заказа).
5. В заказ кладём снимок `unit_price_usd` и курс, по которому продали.

### Выдача

`WaxpeerFulfiller` реализует существующий протокол `Fulfiller`.

- **`fulfill`** → `POST /v1/steam-topup`, `custom_id` = ключ идемпотентности
  заказа. Повтор при таймауте безопасен.
- **`check_status`** → `GET` по `custom_id`:

| Статус Waxpeer        | Наше действие                                             |
| --------------------- | --------------------------------------------------------- |
| `created` / `sending` | ждём                                                      |
| `completed`           | доставлено                                                |
| `canceled`            | деньги вернулись к нам → возвращаем покупателю            |
| `error`               | деньги не вернулись → пометка «разобрать вручную» + алерт |

При `error` заказ помечается `needs_reconciliation` и всплывает в Fulfilment
Inbox; возврат покупателю делает админ оттуда. Автовозврат по строке заказа
рассматривался, но в этой кодовой базе возврат сделан на весь заказ целиком и
только по действию админа — автовозврат одной строки мультитоварного заказа
вернул бы деньги за весь заказ и потребовал бы конвертации валют, которой у
адаптера нет. Это тот же ручной путь, что у всех остальных поставщиков; вынести
его в автоматику — отдельное решение по платёжному модулю.

**Зависшие пополнения.** Пополнение может остаться в `created`/`sending` после
ответа на `fulfill`. У Waxpeer нет вебхука, поэтому `check_status` вызывает
**фоновый поллер** (`apps/scheduler`/`apps/worker`), который добивает
незавершённые задачи до терминального статуса. Без него заказ висел бы вечно —
это блокер для вывода товара покупателям.

### Проверка логина

`GET /v1/steam-topup/validate` за нашим существующим
`POST /catalog/products/{id}/check-player`. Как и у игровых ID — **подсказка, а
не барьер**: ошибка проверки не мешает оплатить.

## Тестирование

- **Контрактные** (respx, записанные ответы): успех, невалидный логин, нехватка
  баланса, каждый из пяти статусов, повторный вызов с тем же `custom_id`.
- **Юнит**: расчёт брутто из нетто при комиссии 0 и ненулевой; округление до
  цента; шлюз доверия (нулевой курс, отклонение вдвое, устаревание, коридор);
  цена = сумма × курс × множитель.
- **Интеграционные**: чекаут с суммой даёт верный итог; сумма вне лимитов
  отклоняется; цена не берётся из запроса клиента.
- Адаптер поставщика — покрытие ≥95% по правилам проекта.

## Вне объёма

- Автоматическое пополнение нашего баланса Waxpeer (пока вручную).
- Автосверка расхождений `give_amount` — только фиксация и уведомление.
- Другие товары Waxpeer (скины, P2P).
- Комиссия Waxpeer ≠ 0 как рабочий режим: закладываем настройку и сверку, но
  запускаемся на нуле.
