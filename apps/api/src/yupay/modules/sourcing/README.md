# `sourcing` — per-SKU fulfillment routing

Решает, **откуда брать товар** на каждую позицию заказа: со склада (`inventory`)
или через адаптер поставщика (`supplier:<slug>`). **Этап 1 — скелет** (ADR-0015).

## Правила

Одна таблица — `sku_sourcing_rules`:

| sku_id | mode                                                     | supplier_slug                                                | …   |
| ------ | -------------------------------------------------------- | ------------------------------------------------------------ | --- |
| UUID   | `auto` / `force_inventory` / `force_supplier` / `manual` | `mock` / `click` / `steam` / … (только для `force_supplier`) |     |

Отсутствие строки = режим `auto`.

## Decision

```python
@dataclass(frozen=True)
class Decision:
    primary: str           # 'inventory' | 'supplier:<slug>'
    fallback: str | None   # 'supplier:<slug>' | None
    strict: bool           # True → no fallback, fail the task on miss
    rule_present: bool
```

| mode                     | primary           | fallback        | strict  |
| ------------------------ | ----------------- | --------------- | ------- |
| `auto` (или нет правила) | `inventory`       | `supplier:mock` | `False` |
| `force_inventory`        | `inventory`       | `None`          | `True`  |
| `force_supplier`         | `supplier:<slug>` | `None`          | `True`  |
| `manual`                 | `supplier:manual` | `None`          | `True`  |

`mode="manual"` — для SKU без supplier-API. Slug у этого режима подразумеваемый
(всегда `manual`), `set_rule` форсит `supplier_slug=NULL`. Заказы по таким SKU
паркуются у `ManualFulfiller` в статусе `in_progress`, и админ обрабатывает их
из очереди ручной выдачи (см. `fulfillment/README.md`, секция «Ручная выдача»).

`DEFAULT_FALLBACK_SUPPLIER` сейчас захардкожен в `mock`. Когда появится первый
живой эквайринг — переедет в `Settings` (отдельный per-currency mapping).

## Сервис

```python
async def resolve_for_sku(db, sku_id) -> Decision: ...
async def set_rule(db, *, sku_id, mode, supplier_slug, admin_id) -> SkuSourcingRule: ...
async def get_rule(db, sku_id) -> SkuSourcingRule | None: ...
async def list_rules(db, limit=200) -> list[SkuSourcingRule]: ...
async def delete_rule(db, sku_id) -> None: ...
```

`set_rule` валидирует: `force_supplier` требует `supplier_slug`. На других режимах
переданный `supplier_slug` молча обнуляется, чтобы строка не несла мусора.

**`auto` теперь детерминирован, когда у SKU два активных маппинга.** До
ADR-0081 `_resolve_auto` брал первую строку `sku_supplier_mapping` без
`ORDER BY` — сходило с рук, пока у каждого top_up SKU был ровно один
активный маппинг. NOVA — первый **резервный** поставщик, и с ним у SKU
законно появляются два (например, `g2b` и `nova`) сразу. Без сортировки
ответ зависел бы от порядка, в котором Postgres решил вернуть строки, — он
может измениться после `VACUUM`, и ничто бы об этом не сообщило. Побеждает
**самый старый** активный маппинг — то есть действующий маршрут;
`supplier_slug` разбивает ничью по `created_at`.

Сортировка (`created_at ASC, supplier_slug ASC`) — **не в запросе**, а в
Python, в `service._pick_auto_mapping_slug`: маппинги грузятся без
`ORDER BY`, и эта чистая функция сама выбирает победителя из уже
загруженного списка. Так у «какой поставщик выигрывает» ровно одно
определение на двух вызывающих — `_resolve_auto` (один SKU, свой запрос) и
батчевый `brand_overview.get_brand_overview` (все SKU бренда одним набором
запросов, без запроса на SKU), — вместо двух реализаций, которые могли бы
разойтись. Кто ищет «где решается порядок» в SQL — не найдёт: решение здесь.

**Резервные поставщики исключены из этого выбора вообще** (`RESERVE_SUPPLIERS`
в `integrations.models`). Одной сортировки мало: она сохраняет маршрут
действующего поставщика, только пока тот вообще есть. У top_up SKU без
маппинга g2b — а это самое обычное состояние бренда — или у SKU, чей
единственный маппинг оператор отключил при переключении, самым старым
оказывается как раз резерв, и SKU начал бы молча покупать у поставщика,
которого никто не выбирал. Резерв достигается только явным
`force_supplier`.

## HTTP (admin only)

```
GET    /api/v1/admin/sourcing/rules                  — все явные правила
GET    /api/v1/admin/sourcing/rules/{sku_id}         — Decision (что сейчас применится)
PUT    /api/v1/admin/sourcing/rules/{sku_id}         — upsert
DELETE /api/v1/admin/sourcing/rules/{sku_id}         — снять, SKU вернётся в `auto`
PUT    /api/v1/admin/sourcing/rules:bulk             — массовое переключение (см. ниже)
GET    /api/v1/admin/sourcing/brands/{brand_slug}    — обзор по бренду (см. ниже)
```

`set_rule` (и поэтому оба `PUT` ниже) отказывает и на неизвестном
`supplier_slug` — сверяется с реальным реестром поставщиков,
`fulfillment.suppliers.REGISTRY`, а не только с фиксированным
`MAPPING_REQUIRED_SUPPLIERS`. Опечатка вроде `waxpeeer` иначе писалась бы как
успешное правило, и каждый заказ падал бы с `get_fulfiller`'s 404 — по одному,
а не при попытке переключить.

`PUT` с `mode=force_supplier` на поставщика, которому нужен маппинг (G2B,
G-Engine, NOVA — `MAPPING_REQUIRED_SUPPLIERS` в `integrations.models`), отказывает, если
у SKU нет активной строки `sku_supplier_mapping` на него. Иначе правило
«применилось», а каждый заказ падает в inbox с `no active mapping` — по одному.
Waxpeer маппинга не требует и не проверяется.

`PUT .../rules:bulk` (`bulk_rules.bulk_set_rules`) применяет одно решение —
`{sku_ids, mode, supplier_slug}` — к списку SKU (до 100 за запрос) сразу.
Каждый SKU — своя единица работы (`SAVEPOINT` на итерацию): один SKU без
активного маппинга на форсируемого поставщика, или с неизвестным
`supplier_slug`, проваливается по имени (`{sku_id, ok: false, error: "..."}`),
а остальные всё равно записываются — частичный успех, а не всё-или-ничего.
Тот же `SAVEPOINT` ловит и настоящую ошибку уровня БД: `set_rule` — это
SELECT-затем-INSERT без `ON CONFLICT`, так что два админа, массово
переключающие пересекающиеся выборки SKU, могут словить unique-violation на
PK `sku_sourcing_rules`; это тоже репортится по имени, а не роняет весь
батч. `mode=auto` удаляет явное правило, как `DELETE`, и не ошибается на
SKU, у которого правила и так не было.

**Контракт `Idempotency-Key` на `:bulk`.** Оба `PUT` принимают
`Idempotency-Key` (§9 AGENTS.md) — повтор с тем же ключом отдаёт сохранённый
ответ, не перезапуская запись, **даже если в первый раз упали все элементы**
(`0/100 ok`). Это корректная replay-семантика — тело первого ответа не зависит
от того, сколько элементов в нём `ok`, — но ловушка для очевидного цикла
оператора: увидеть `0/100`, исправить причину (например, создать недостающий
маппинг), нажать Retry с тем же ключом и получить тот же старый `0/100` без
единой новой записи. Повтор также игнорирует **другое** тело запроса — ключ,
а не содержимое, решает, что реплеится. Поведение не меняется намеренно:
сделать `0/100` особым случаем было бы третьей семантикой идемпотентности
рядом с двумя существующими. **Один `Idempotency-Key` — одна попытка,
никогда не выборка SKU**: повтор после того, как оператор что-то исправил,
должен прийти с новым ключом.

`GET .../brands/{brand_slug}` (`brand_overview.get_brand_overview`) — экран
«обзор по бренду»: одна строка на каждый активный SKU бренда, с полем
`primary`/`rule_present` (тот же `Decision`, посчитанный из тех же
батч-загруженных данных, что и `resolve_for_sku`) и списком `suppliers` —
сравнением по кандидатам-поставщикам (объединение трёх множеств: сами
мапленные поставщики, фиксированный `MAPPING_REQUIRED_SUPPLIERS` и те, кого
называет `force_supplier`-правило) с последней известной ценой из
`supplier_price_history`. Пять ограниченных запросов независимо от числа SKU
(без N+1), ограничение — `MAX_BRAND_OVERVIEW_SKUS` (500) активных SKU на
бренд. Строка с битым правилом (`force_supplier` без `supplier_slug`,
записанным в обход `set_rule`) не роняет весь ответ — репортится как
`primary="invalid"`, остальные строки грузятся как обычно.

**`cost_source`** на каждой записи `suppliers` говорит, откуда взялся
`latest_cost_usdt` — `supplier_price_history` фиксирует _изменение_ цены, а
не текущее состояние, так что у поставщика, чья цена просто ни разу не
менялась с момента создания маппинга, нет вообще ни одной строки истории,
хотя его цена прямо сейчас лежит в `Sku.cost_usdt` (на проде у каждого SKU
Free Fire — ноль строк истории g2b при том, что `cost_usdt` хранит цену g2b
до цента). Раньше это рендерилось как «цена не снята», что вводило в
заблуждение именно про того поставщика, у которого мы прямо сейчас
покупаем. Три значения:

- `"history"` — есть строка `supplier_price_history`; `latest_cost_usdt` /
  `captured_at` — из неё.
- `"current"` — строки истории нет, но выполняются все три условия сразу:
  именно на этого поставщика маршрутизирован SKU
  (`integrations.cost_refresh.is_routed_supplier` — та же проверка, которой
  сам `cost_refresh` решает, кому можно писать `Sku.cost_usdt`, ADR-0083
  Decision 1), сбор цен вообще дотягивается до этого поставщика
  (`integrations.cost_refresh.supports_price_collection` — сейчас это
  только g2b и nova, тот же список, которым пользуется диспетчер
  `refresh_sku_cost_for_mapping`, а не отдельный захардкоженный дубликат),
  и у SKU вообще есть `cost_usdt` (не `None`). `latest_cost_usdt` — это
  `Sku.cost_usdt`, `captured_at` — `None` (это не точечный снимок во
  времени).
- `None` — любое из трёх условий не выполнено: цена этого поставщика нам
  действительно неизвестна, либо честно приписать её именно ему нельзя.
  `latest_cost_usdt` остаётся `None`, как и до появления этого поля.

**Почему второе условие обязательно, а не только маршрутизация.** У сбора
цен сегодня есть реализация только для g2b и nova (`cost_refresh` отвечает
«сбор цен не поддержан» для всех остальных). `Sku.cost_usdt` при этом
привязан к тому поставщику, которого называет `is_routed_supplier` — но
если SKU принудительно переключён на `gengine` или `waxpeer`, в этой
колонке лежит наша себестоимость, которую этот поставщик никогда не
устанавливал: это цена _предыдущего_ маршрутизированного поставщика,
оставшаяся с момента до переключения. Без второго условия такая цена
выигрывала бы сравнение по цене на равных с ценами, которые мы
действительно у этого поставщика сняли.

**Остаточный случай, который это не закрывает.** Окно между переключением
маршрута и следующим часовым `refresh-all-prices` — маршрутизированный
поставщик поддерживается сбором цен (g2b или nova), но ещё не был
опрошен после переключения, так что `Sku.cost_usdt` всё ещё хранит число
_предыдущего_ маршрутизированного поставщика. `cost_source` в этом окне
всё равно репортит `"current"` — оба условия формально выполнены — но
значение может быть устаревшим (ценой поставщика, с которого только что
переключились), а не ценой нового. Часовой рефреш закрывает это окно
сам по себе; ничего в этом эндпоинте его специально не укорачивает.

## Инвариант: `force_inventory` только для `voucher`

`set_rule` отказывает на `mode="force_inventory"`, если продукт SKU —
`top_up`. У top_up SKU нечего выдавать со склада (баланс игрока пополняет
живой вызов поставщика), так что `force_inventory` там значило бы
`Decision(primary="inventory", fallback=None, strict=True)` — гарантированный
`NoStockError` без фолбэка на каждый заказ, вместо обычного auto-маршрута,
который хотя бы дойдёт до поставщика или ручной очереди. Симметричная
половина того же правила — на стороне «положить код на склад» — это
`inventory.service._reject_top_up_sku`: `bulk_upload` отказывает загружать
коды для top_up SKU тем же способом (и это верно без оговорок —
`InventoryCode(` конструируется ровно в одном месте, внутри `bulk_upload`).
Массовый эндпоинт (`rules:bulk`) наследует проверку без изменений — она
внутри `set_rule`, который `bulk_set_rules` вызывает на каждый SKU, так что
отказ репортится по имени SKU, а не роняет весь батч.

**Эта гарантия — про вызывающих через сервис, не про таблицу.** «Наследует»
выше значит: любой код, который зовёт `sourcing.service.set_rule` (HTTP-роут,
`bulk_set_rules`, будущий вызывающий), не может записать `force_inventory`
на top_up SKU — проверка внутри самой функции. Код, который пишет
`sku_sourcing_rules` напрямую через ORM или сырой SQL, в эту гарантию не
входит и её обходит. Два seed-скрипта делают именно так —
`scripts/seed/2026-09-17_nova_mappings.py` и
`scripts/seed/2026-09-18_free_fire_nova_only.py` — оба зовут
`pg_insert(SkuSourcingRule).on_conflict_do_update(...)` напрямую, минуя
`set_rule`. Сегодня это не пробивает guard только потому, что оба
захардкожены на `mode="force_supplier"`; ничто не мешает будущему seed-у
записать туда `force_inventory` для top_up SKU в обход этой проверки.
(комментарий в `brand_overview.py` про битую строку `force_supplier` без
`supplier_slug` говорит то же самое про прямые записи — та же честность
здесь.)

## Admin-экран «Sourcing по бренду»

`/sourcing/brands/:brandSlug` (`apps/admin/src/features/sourcing/BrandSourcingPage.tsx`) —
единственная страница, на которой оператор реально сравнивает поставщиков и переключает
несколько SKU разом; редактор одного SKU (`/sourcing`, `SourcingPage.tsx`) остаётся для
точечной правки, но не может ни сравнить, ни переключить больше одного за раз.

Оператор выбирает бренд из списка (`GET /admin/catalog/brands`) и видит таблицу — один ряд на
каждый активный SKU, столбец на каждого поставщика-кандидата с последней известной ценой
(самая дешёвая подсвечена, отсутствие маппинга — видимый пропуск, а не пустая ячейка), текущий
маршрут и цена/маржа. Строка переключается своим собственным контролом; отметив несколько
строк, оператор применяет одно решение (`mode` + при `force_supplier` — поставщика) сразу ко
всем отмеченным. Поставщик без активного маппинга на этот SKU в списке кандидатов недоступен
для выбора, с причиной рядом — экран отказывает до отправки запроса, а не после 422 от
`set_rule`.

**И построчное переключение, и шапочное массовое — это один и тот же вызов.** Оба идут через
`switchSkusChunked` (`bulkSwitch.ts`) в `PUT .../rules:bulk`, даже когда отмечен один SKU. Это
намеренно, а не совпадение реализации: так на весь экран есть ровно один путь записи, а не два
слегка разных, — и именно он один минтит `Idempotency-Key` (свежий на каждый HTTP-запрос, никогда
не переиспользуемый — см. `Idempotency-Key`-контракт выше) и режет выборку на куски по 100 SKU
(`MAX_BULK_SKU_IDS`) до отправки, а не полагается на то, что оператор никогда не отметит бренд
крупнее серверного лимита. Частичный отказ — обычный ответ, не исключение: неудачные SKU
остаются отмеченными с текстом причины, успешные снимаются с отметки, оператор чинит и
повторяет уже с новым ключом.

Ниже остаётся и таблица явных правил (`SourcingPage.tsx`) — теперь с брендом, продуктом и
номиналом рядом с кодом, текстовым фильтром и фильтрами по поставщику и режиму, чтобы её тоже
можно было искать, а не только листать.

## Связь с `fulfillment`

`fulfillment.service.start_for_order` зовёт `sourcing.resolve_for_sku(sku_id)`
для каждого item и пишет `fulfillment_tasks.supplier = 'inventory'` или
`fulfillment_tasks.supplier = '<slug>'`. Запись в `task.supplier` — это
**фактически выбранный маршрут**, не модель правила. При фолбэке (auto +
no-stock) `task.supplier` перезаписывается на slug провайдера, и в
`fulfillment_attempts` появляется строка `{route_switch: <slug>, reason: 'inventory_no_stock'}`.

## Что отложено

1. **Per-region routing** — сейчас правило per-SKU; для крупных каталогов
   нужно «все Spotify-региона EU → supplier:steam».
2. **Cost-based routing** — выбирать дешевле (наш склад vs supplier-margin),
   с фолбэком при изменении цен.
3. **A/B routing** — % трафика на нового поставщика для прогрева.
