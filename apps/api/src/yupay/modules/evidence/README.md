# `evidence` — доказательства для оспариваний

Снимок контекста запроса, из которого был оформлен заказ. Нужен ровно для одного:
ответить эквайеру, когда держатель карты оспаривает платёж, и уложиться в его сроки.

Почему это вообще существует и почему нарушает §9 AGENTS.md — см.
[`docs/decisions/0044-chargeback-evidence-capture.md`](../../../../../../docs/decisions/0044-chargeback-evidence-capture.md).

## Что хранится

Одна строка на заказ в `order_evidence`, пишется один раз и не обновляется:

| Поле              | Зачем в пакете доказательств                                    |
| ----------------- | --------------------------------------------------------------- |
| `ip`              | Адрес плательщика. Тип `INET` — Postgres не даст записать мусор |
| `user_agent`      | Браузер и платформа                                             |
| `accept_language` | Язык интерфейса на момент покупки                               |
| `client_hints`    | Часовой пояс, локаль, экран — подтверждают согласованность IP   |
| `purge_after`     | Дата удаления, проставленная при захвате                        |

Вторая половина пакета — `order_events` из модуля `orders`: лента статусов с временем,
которая отвечает на вопрос «когда и кому выдали».

## Три вещи, которые легко сломать

**Захват не имеет права сорвать продажу.** Вызов идёт _после_ создания заказа и внутри
точки сохранения. Одного `try/except` недостаточно: транзакция запроса коммитится уже
после возврата из роута, поэтому упавший запрос отравляет её и заказ теряется на коммите —
ровно та авария, от которой защита и придумана. Есть тест, который это проверяет.

**Повтор не должен переписывать захват.** Тот же `Idempotency-Key` возвращает исходный
заказ; повтор мог прийти с другого адреса (телефон сменил сеть). Побеждает первая запись —
`ON CONFLICT DO NOTHING`.

**Срок удаления берётся из строки, а не из конфига.** Сократив политику завтра, мы не
должны задним числом продлевать жизнь данным, собранным под вчерашнее обещание.

## Достоверность IP

Держится на том, что пограничный прокси **перезаписывает** `X-Forwarded-For` реальным
адресом пира (`header_up X-Forwarded-For {remote_host}` в `infra/edge/Caddyfile`), а не
дописывает к нему. Если это когда-нибудь поменяют на дописывание, таблица начнёт хранить
то, что подсунул вызывающий, — и перестанет быть доказательством. Разбор адреса живёт в
`core/client_ip` в одном экземпляре: лимитер, защита авторизации и этот модуль обязаны
одинаково отвечать на вопрос «кто звонил».

## Кто читает

`GET /api/v1/admin/orders/{order_id}/evidence` за `require_admin`. Публичного аналога нет
и быть не должно: это единственная точка API, отдающая нехэшированный IP.

**Каждое чтение пишется в ленту заказа** событием `admin.evidence_viewed` с указанием
админа — по тому же правилу, что и чтение выданных кодов (`admin.deliveries_viewed`):
раз данные настолько чувствительные, что мы держим их в отдельной таблице со сроком
удаления, то «кто смотрел адрес покупателя» обязано быть вопросом с ответом. Событие
добавляется _после_ сборки ответа: пакет уходит эквайеру, и наш собственный журнал
доступа — не часть ответа на его запрос.

В админке это карточка «Контекст покупателя» на странице заказа
(`apps/admin/src/features/orders/EvidenceCard.tsx`). Данные не запрашиваются, пока
оператор не нажмёт «Показать контекст», — иначе аудит записывал бы просмотр при каждом
открытии страницы заказа, а IP висел бы на экране во время демонстрации экрана.
